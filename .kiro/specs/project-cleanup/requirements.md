# Requirements Document

## Introduction

The Catch-22 project currently uses npm as its package manager alongside a pre-existing `bun.lock` file, resulting in dual lock files and an inconsistent toolchain. The project also contains a `scripts/` directory populated with one-time WordPress-to-Supabase migration scripts that have already been executed and are no longer needed. Additionally, `.DS_Store` files and other OS/editor artifacts are scattered throughout the repository.

This feature covers the full project cleanup: migrating the package manager from npm to Bun, removing legacy migration scripts, eliminating stale artifacts, and verifying the project builds and runs cleanly under Bun.

---

## Glossary

- **Bun**: A fast JavaScript runtime and package manager used as a drop-in replacement for Node.js/npm in this project.
- **bun.lock**: The Bun-native lockfile that replaces `package-lock.json`.
- **package-lock.json**: The npm-generated lockfile to be removed after Bun migration.
- **Migration_Script**: A one-time-use `.mjs` script in `scripts/` that was written to migrate data from the legacy WordPress/Elementor system into Supabase. These scripts have already been executed.
- **Utility_Script**: An ongoing-use `.mjs` script in `scripts/` that provides operational value post-migration (e.g., health checks, Stripe sync).
- **Artifact**: Any file that is not part of the application source and should not be committed to version control (e.g., `.DS_Store`, `node_modules/`, stale lock files).
- **Project**: The Catch-22 Next.js 16 headless e-commerce application at `catch-22.co.nz`.
- **CI_Environment**: Any automated build or deployment pipeline that runs `bun install` and `bun run build`.

## Requirements

### Requirement 1: Migrate Package Manager from npm to Bun

**User Story:** As a developer, I want to use Bun as the sole package manager, so that the project has a single, consistent, fast toolchain without conflicting lock files.

#### Acceptance Criteria

1. THE Project SHALL contain a `bun.lock` file as the only lock file at the repository root.
2. WHEN `package-lock.json` exists in the repository, THE Project SHALL remove it so that npm is no longer the authoritative package manager.
3. THE Project SHALL retain `package.json` with all existing dependencies and scripts unchanged.
4. WHEN a developer runs `bun install`, THE Project SHALL install all dependencies successfully without errors.
5. WHEN a developer runs `bun run build`, THE Project SHALL produce a successful Next.js production build.
6. WHEN a developer runs `bun run dev`, THE Project SHALL start the Next.js development server without errors.
7. WHEN a developer runs `bun run lint`, THE Project SHALL execute ESLint without errors.
8. THE `node_modules/` directory SHALL be regenerated by Bun after the migration so that all installed packages are managed by Bun.

---

### Requirement 2: Remove Legacy One-Time Migration Scripts

**User Story:** As a developer, I want to remove scripts that were only needed during the WordPress-to-Supabase migration, so that the `scripts/` directory contains only operationally relevant tooling.

#### Acceptance Criteria

1. THE Project SHALL remove the following one-time migration scripts from `scripts/`:
   - `migrate.mjs`
   - `migrate_all_schemas.mjs`
   - `migrate_gallery_media.mjs`
   - `migrate_internal_links.mjs`
   - `migrate_media.mjs`
   - `migrate_submissions.mjs`
   - `upload_all_media.mjs`
   - `upload_final.mjs`
   - `upload_products.mjs`
   - `upload_users_orders.mjs`
   - `cleanup_spam.mjs`
   - `deep_cleanup.mjs`
2. THE Project SHALL retain the following ongoing utility scripts in `scripts/`:
   - `health_check.mjs`
   - `sync_stripe.mjs`
   - `verify_migration.mjs`
   - `audit_images.mjs`
3. WHEN the `scripts/` directory is reviewed after cleanup, THE Project SHALL contain only the four utility scripts listed in criterion 2.

---

### Requirement 3: Remove Hardcoded Credentials from Scripts

**User Story:** As a developer, I want to ensure no scripts contain hardcoded database credentials, so that sensitive connection strings are not committed to version control.

#### Acceptance Criteria

1. THE Project SHALL contain no hardcoded database connection strings, passwords, or API keys in any file tracked by git.
2. WHEN `migrate.mjs` is removed as part of Requirement 2, THE Project SHALL no longer contain the hardcoded PostgreSQL connection string that was present in that file.
3. IF any remaining utility script contains a hardcoded credential, THEN THE Developer SHALL replace it with a reference to the corresponding environment variable defined in `.env.local`.

---

### Requirement 4: Remove OS and Editor Artifacts

**User Story:** As a developer, I want to remove `.DS_Store` and other OS-generated files from the repository, so that the working tree is clean and these files cannot be accidentally committed in future.

#### Acceptance Criteria

1. THE Project SHALL remove all `.DS_Store` files currently tracked or present in the repository, including those in:
   - The repository root (`/.DS_Store`)
   - `.trunk/.DS_Store`
   - `src/.DS_Store`
   - `supabase/.DS_Store`
2. THE `.gitignore` file SHALL include an entry for `.DS_Store` so that macOS metadata files are excluded from future commits.
3. WHEN a developer creates a new file on macOS, THE `.gitignore` SHALL prevent `.DS_Store` files from appearing as untracked changes in `git status`.

---

### Requirement 5: Verify Clean Build and Runtime Under Bun

**User Story:** As a developer, I want to confirm the project builds and starts correctly after all cleanup steps, so that I can be confident the migration has not broken anything before proceeding to Final QA.

#### Acceptance Criteria

1. WHEN all cleanup steps from Requirements 1–4 are complete, THE Project SHALL produce a successful `bun run build` output with zero errors.
2. WHEN `bun run build` completes successfully, THE Project SHALL generate a `.next/` build directory containing the production-ready application.
3. WHEN `bun run lint` is executed after cleanup, THE Project SHALL report zero ESLint errors.
4. IF `bun run build` produces TypeScript or compilation errors after cleanup, THEN THE Developer SHALL resolve those errors before marking this feature complete.
5. THE Project SHALL NOT introduce any new runtime dependencies or devDependencies as part of this cleanup.

---

### Requirement 6: Update Developer Documentation

**User Story:** As a developer, I want the project's documentation to reflect Bun as the package manager, so that any contributor or CI pipeline uses the correct toolchain from the start.

#### Acceptance Criteria

1. THE `README.md` SHALL reference `bun install` instead of `npm install` for the project setup instructions.
2. THE `README.md` SHALL reference `bun run dev`, `bun run build`, and `bun run lint` instead of their `npm run` equivalents.
3. WHERE the `AGENTS.md` or `CLAUDE.md` files reference npm commands, THE Project SHALL update those references to use Bun equivalents.
4. WHEN a new developer follows the README setup instructions, THE Project SHALL be runnable using only Bun without requiring npm to be installed.
